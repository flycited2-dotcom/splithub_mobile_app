# Playbook: как сделать и выпустить B2B мобильное приложение (Android-first, РФ)

Выжимка компетенций и рецептов на основе проекта SplitHub. Цель — чтобы будущее
аналогичное приложение (каталог/заказы/уведомления для гаджетов или любой ниши)
можно было собрать и выпустить, не наступая на те же грабли.

---

## 1. Стек и ключевое решение архитектуры

- **Клиент:** React Native + **Expo (bare workflow)** на TypeScript. Bare = папка
  `android/` (и `ios/`) закоммичена в репо → воспроизводимая нативная сборка, полный
  контроль, при этом удобства Expo (expo-router, expo-modules).
- **Бэкенд:** переиспользуем backend существующего **сайта** (PHP + SQLite), добавляя
  отдельный «мобильный» API-роутер. Один источник данных для сайта и приложения —
  общая таблица `users`, общие заказы. Не плодить второй бэкенд.
- **Почему так:** один разработчик/малая команда, B2B-ниша, бюджет. Общий код RN для
  Android+iOS, общий бэкенд с сайтом → минимум дублирования.

**Принцип:** новый мобильный функционал = тонкий нативный/RN-слой поверх уже
работающего веб-бэкенда. Сначала пробрось данные, потом полируй UX.

## 2. Воспроизводимая локальная сборка на Windows (выстрадано)

Собираем APK локально (не EAS), чтобы не зависеть от облака и держать keystore у себя.

- **patch-package** (+ postinstall): фиксы в `node_modules` (cmake и т.п.) коммитятся
  как патчи и применяются автоматически. Сборка перестаёт быть «работает только у меня».
- **`.gitattributes`** держит `gradlew` как LF (иначе сломается на Windows).
- **VPN обязателен:** Gradle тянет зависимости из **Google Maven** (`dl.google.com`),
  который гео-блокируется из РФ. Без VPN сборка падает на скачивании. (Это не «новый
  инструмент» — `google()` стоит в `android/build.gradle`, как в любом Android-проекте.)
- **Windows MAX_PATH (260):** глубокие C++ модули (reanimated/worklets) упираются в
  лимит длины пути. Фикс — патчами переносить `.cxx` на короткий путь
  (`buildStagingDirectory "C:/wkx"`), только под Windows.
- **НЕ добавлять нативные модули с New-Arch codegen, лежащие глубоко в node_modules:**
  их `.cxx` компилируется внутри приложения по пути ~380 символов → MAX_PATH. Решение —
  **встроенный Kotlin-модуль в приложении** (без RN codegen, без `.cxx`).
- **Временный файловый лок при упаковке:** `:app:packageRelease` иногда падает с
  generic ошибкой (антивирус/файловый хэндл на Windows). Лечение — **просто повторить**
  (большинство задач закэшировано, повтор 1 минута).
- **Команда сборки** (универсальная, все ABI ~12 мин):
  ```
  CMAKE_VERSION=3.31.6 JAVA_HOME=".../jdk-17" ANDROID_HOME=".../Android/Sdk" \
  bash android/gradlew -p android :app:assembleRelease --no-daemon
  ```
  Для теста на устройстве — `-PreactNativeArchitectures=arm64-v8a` (быстрее, ~99% телефонов).

## 3. Подпись и жизненный цикл keystore

- Релизный **keystore** (`release.jks`) + пароли (`keystore.properties`) — **gitignored**.
- ⚠️ **Главное правило сторов:** все обновления подписываются ТЕМ ЖЕ ключом. Потеря
  keystore = невозможно обновлять приложение (придётся публиковать заново, теряя
  установки/отзывы). → **Офлайн-бэкап keystore+паролей вне репо и вне одного диска.**
- Проверка подписи APK: `apksigner verify --print-certs app.apk` (сверять SHA-256
  сертификата). Бамп версии перед релизом: `versionCode`++ в `android/app/build.gradle`
  (и `app.json` для консистентности).

## 4. Распространение — честные реалии

### Android, раздача по ссылке (sideload)
- Самый быстрый канал: подписанный APK на своём https-хостинге + простая страница
  установки. Ставится `adb install -r` или скачиванием на телефон.
- **Play Protect нельзя обойти при sideload:** «приложение заблокировано / не
  рекомендуется устанавливать» — встроенная защита Android для любого не-сторового APK.
  Ни подпись, ни сервер это не убирают. **Единственное решение — публикация в магазине.**
- **HTTPS обязателен:** если страница/файл отдаются по http, браузер пугает
  «незащищённый файл». Фикс — абсолютная https-ссылка на APK + редирект http→https в
  `.htaccess` (loop-safe через `X-Forwarded-Proto`, чтобы не словить петлю на proxy-SSL).

### RuStore (рекомендуемый стор для РФ)
- Принимает **APK напрямую** (AAB не обязателен). Регистрация разработчика — ИП
  (ОГРНИП/ИНН/адрес), оферта (возможно Госключ). Нужны: иконка 512×512, privacy-URL,
  скриншоты, описание. После публикации — установка в 1 тап без предупреждений.

### Google Play
- Нужен AAB, $25 разовый, строже модерация, в РФ — ограничения доступа/оплат разработчика.

### iOS (iPhone)
- Только macOS/облако (EAS/Codemagic) для сборки; Apple Developer $99/год; **нет
  sideload** — только TestFlight/App Store; push — отдельный ключ **APNs**.
- Прагматично: **сайт работает на iPhone в Safari** (можно «На экран Домой» как PWA) —
  закрывает потребность до нативного iOS-аппа.

## 5. Серверные паттерны (PHP + SQLite)

- **Один файл-роутер на платформу:** `api/mobile.php` (приложение), `api/auth.php`
  (сайт). Внутри `switch($action)` / `if ($action===...)`. Общая логика — в `lib/`.
- **Авторизация:** приложение — bearer-токены (таблица `mobile_sessions`,
  `Authorization: Bearer`), сайт — PHP-сессии. Пароли — `password_hash` (bcrypt).
- **Миграции SQLite — идемпотентные, на каждом старте:** `PRAGMA table_info(...)` +
  `ALTER TABLE ADD COLUMN` в `try{}`. `CREATE TABLE IF NOT EXISTS`. Безопасно для
  существующих данных. `getenv('DB_PATH')` для подмены БД в тестах.
- **Push:** через Expo (`exp.host/.../push/send`) → Expo маршрутизирует в FCM (Android)
  и APNs (iOS). Кампании/доставки логировать в таблицы. В РФ регистрация Expo
  push-токена гео-блокируется (нужен VPN при регистрации), но **доставка** работает.
- **Конфиг/секреты** на сервере — вне репо (`config.php` в `.htaccess` deny).

## 6. Рецепт: восстановление пароля без SMS (email-код + поэтапный выкат)

Частая задача и грабли. Что сработало:

- **Канал — email-код** (6 цифр), единый для сайта и приложения (без deep-link,
  пользователь остаётся в приложении). SMS в РФ — дорого/сложно, не брали.
- **Хранение кода:** только sha256-хэш в таблице `password_resets`, срок 15 мин,
  одноразовый, ≤5 попыток, rate-limit, прошлые коды гасятся. При сбросе — гасить сессии.
- **Восстановление только по email** (не «телефон или email»): люди вводят телефон по
  привычке, а код уходит на почту → путаница. Поле строго «Ваш email».
- **Email обязателен при регистрации**, НО выкат **без простоя** через флаг
  `app_settings.email_required` (`'0'` → опционален, `'1'` → обязателен). Сначала
  деплой бэкенда с флагом `'0'` (ничего не ломается), потом фронты собирают email,
  потом «флип» флага одной строкой `UPDATE` — без передеплоя. Иначе обязательный email
  на сервере ломает старые установки/формы без поля email.
- **Старые пользователи без email:** баннер «Привяжите email» при входе + (опц.)
  push-кампания + **менеджерский fallback** (в админке сброс пароля + привязка email).
  При «email не найден» — текст «обратитесь к менеджеру», а не сухое «не найдено».
- **Не забыть пробросить поле** (`email`) во все ответы `login/profile/register` —
  иначе клиент не знает, есть ли email, и баннеры/логика врут.

## 7. Гигиена и безопасность деплоя

- **Креды — только из файла вне репо** (`~/.splithub-deploy.json`) или env, никогда в
  командной строке и не в коде (иначе и утечка, и блокировки авто-режимов).
- **Перед прод-правкой — бэкап:** `cp -p file file.bak-<stamp>`; после — `php -l`.
- **Дымовой тест после деплоя:** реальные HTTP-запросы (register/reset/...), затем
  **удалить созданные тест-данные** по их id.
- **Превью до прода:** выкладывать на отдельную `preview.html` (с `noindex`),
  показывать пользователю, и только после одобрения — на боевой `index.html`
  (с бэкапом). Особенно для проверки **трения на входе** (лишние поля отпугивают).
- **Деструктивные операции на проде** (DELETE, правка `.htaccess`) — с явного согласия
  и с авто-откатом, где возможно.

## 8. Тестирование

- **Серверный PHP:** если PHP нет локально — гонять тесты **на сервере по SSH** на
  **временной SQLite** (`DB_PATH=/tmp/...`, прод не трогаем). TDD: падающий тест →
  реализация → зелёный. `php -l` всех файлов перед деплоем.
- **RN:** `tsc --noEmit` + `jest`. Мокать контекст сессии (не забывать добавлять новые
  методы в моки — иначе tsc красный).
- **E2E на устройстве:** ADB + `input tap/text` по координатам + `exec-out screencap` →
  читать скриншоты, вести пользователя по шагам. Незаменимо для проверки реального UX.
- **Статическая проверка APK:** распаковать (zip) и грепнуть JS-бандл (`index.android.bundle`)
  на правильный API-URL — ловит «собрано против staging/localhost».

## 9. Грабли-памятка (быстрый список)

| Симптом | Причина / фикс |
|---|---|
| Сборка падает на скачивании зависимостей | Нет VPN (Google Maven гео-блок) |
| `packageRelease FAILED` без причины | Временный файловый лок на Windows → повторить |
| C++ модуль не собирается, путь длинный | MAX_PATH → `.cxx` на `C:/wkx`, или встроенный Kotlin-модуль |
| «Незащищённый файл» при скачивании APK | http вместо https → абсолютная https-ссылка + редирект |
| «Play Protect заблокировал» | Любой sideload → решает только публикация в сторе |
| Свежая установка «уже залогинена» | Android auto-backup восстановил токен → обдумать `allowBackup=false` |
| Обязательный email сломал регистрацию | Выкатили флип раньше фронтов → флаг поэтапного выката |
| Push-токен 403 при регистрации в РФ | Гео-блок Expo → VPN при регистрации; доставка работает без VPN |

## 10. Процесс (как вести разработку фичи)

1. **Brainstorm → Spec → Plan → Execute** (зафиксировать решения в `docs/.../specs` и
   `.../plans`). Уточнять по одному вопросу, предлагать 2–3 подхода с рекомендацией.
2. **Заземлять дизайн на факты** (читать реальную схему БД, как шлётся почта, как
   устроены роутеры) — не выдумывать.
3. **Сначала превью/трение, потом прод.** Показывать пользователю визуально (ссылка),
   а не словами.
4. **Маленькие безопасные шаги + частые коммиты**, бэкапы перед прод-правками,
   проверка результата реальной командой (evidence before claims).

- [ ] Release keystore + **офлайн-бэкап вне репо/диска**.
- [ ] Мобильный API-роутер + bearer-сессии + идемпотентные миграции.

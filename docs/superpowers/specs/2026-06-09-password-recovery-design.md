# Восстановление доступа (сброс пароля) — дизайн

Дата: 2026-06-09
Статус: одобрен пользователем (Секции 1–3), ожидает финального ревью спеки.

## Проблема

Клиент, забывший пароль, застревает: регистрация отказывает («телефон уже
зарегистрирован»), вход не пускает, восстановления пароля **нет нигде** (ни сайт,
ни приложение, ни сервер). Подтверждено диагностикой 2026-06-08.

## Цель и решения (согласовано)

- Самостоятельное восстановление **по email** + ручной **fallback через менеджера**.
- Email **обязателен** для новых регистраций (минимальное трение — одно поле).
- Существующим без email — мягкое предложение добавить email в профиле; пока нет —
  сброс через менеджера.
- Внедряем **и на сайте, и в приложении** (общий бэкенд, разные фронты).
- Механизм: **6-значный код на email** (подход A) — единый путь для приложения и
  сайта, без deep-link'ов.

## Не входит (YAGNI)

- Отдельный экран «сменить пароль, будучи залогиненным».
- Telegram-канал восстановления (ограничение: бот не пишет первым; нужен chat_id).
- SMS (нет инфраструктуры).

## Секция 1 — Архитектура и данные

**Архитектура:** общий модуль `api/lib/password_reset.php` со всей логикой; его
подключают `api/mobile.php` (приложение) и `api/auth.php` (сайт). Дублирования нет.
Оба роутера дают одинаковые действия. Фронт: RN-экраны в приложении; формы в
`index.html` на сайте.

**Данные:**
1. В `users` добавить `email TEXT DEFAULT ""` (пустая у существующих). Миграция в
   `db/init.php` через `PRAGMA table_info(users)` — безопасно для текущих данных.
2. Новая таблица кодов:
   ```sql
   CREATE TABLE IF NOT EXISTS password_resets (
     id INTEGER PRIMARY KEY AUTOINCREMENT,
     user_id INTEGER NOT NULL,
     code_hash TEXT NOT NULL,        -- sha256 кода, не сам код
     expires_at TEXT NOT NULL,       -- now + 15 минут
     attempts INTEGER NOT NULL DEFAULT 0,
     used INTEGER NOT NULL DEFAULT 0,
     created_at TEXT DEFAULT CURRENT_TIMESTAMP,
     FOREIGN KEY (user_id) REFERENCES users(id)
   );
   ```
Письмо шлётся существующим `mail()` с `From: info@splithub.ru`.

## Секция 2 — Бэкенд: логика и endpoint'ы

**`api/lib/password_reset.php`:**

- `requestPasswordReset($identifier)` — `identifier` = телефон **или** email:
  - найден + есть email → 6-значный код, запись `code_hash`+`expires_at`, гашение
    прошлых неиспользованных кодов юзера, письмо. Ответ `sent` + маска `i***@m***.ru`.
  - найден, email пуст → `no_email` (UI: обратитесь к менеджеру + контакты).
  - не найден → `not_found`.
  - rate-limit: ≤5 запросов/час на пользователя (по `created_at`).
- `confirmPasswordReset($identifier, $code, $newPassword)`:
  - берём последний неиспользованный непросроченный код; нет → `CODE_EXPIRED`;
    `attempts++`, >5 → `TOO_MANY_ATTEMPTS`; неверный код → `INVALID_CODE`
    (+ остаток попыток); пароль <4 → `INVALID_PASSWORD`.
  - успех → `password_hash` = bcrypt(новый), код `used=1`, **гасим все
    `mobile_sessions` юзера**.

**Роутеры (`mobile.php` и `auth.php`):**
- `request_password_reset` (POST `{identifier}`).
- `reset_password` (POST `{identifier, code, password}`) → при успехе авто-вход
  (mobile: `issueMobileToken`; web: установка сессии).
- `register`: добавить обязательный `email` (`filter_var(..., FILTER_VALIDATE_EMAIL)`),
  сохранять в `users.email`.
- `update_email` (POST, нужна авторизация): валидация + сохранение email (для старых).

**Менеджерский fallback (админка):**
- `api/admin.php`: действие `reset_client_password` (под ролью admin) — задать новый
  пароль клиенту.
- `admin.html`: кнопка «Сбросить пароль» в строке клиента → модалка.

## Секция 3 — Фронт, безопасность, тесты

**Приложение (RN):**
- Экран входа: ссылка «Забыли пароль?» → экран ввода телефона/email → экран ввода
  кода + нового пароля → авто-вход → профиль.
- Регистрация: поле **Email (обязательное)** с подписью «понадобится для
  восстановления доступа».
- Профиль: если email пуст — баннер «Добавьте email для восстановления» + действие.

**Сайт (`index.html`):**
- Модалка входа: «Забыли пароль?» → форма (identifier → код + пароль).
- Форма регистрации: поле **Email (обязательное)**.
- Дашборд/профиль: подсказка добавить email, если пуст.

**Безопасность:** код 6 цифр, в БД только хэш; срок 15 мин; одноразовый; ≤5 попыток;
прошлые коды гасятся; rate-limit; при сбросе гасятся сессии; `From: info@splithub.ru`.
Перечисление аккаунтов (`not_found`/`no_email`) — осознанный компромисс для
доверенной B2B-базы (помогает реальным клиентам понять, что делать).

**Тесты:**
- Сервер: PHP-CLI на временной SQLite — happy path, неверный код, просрочка,
  превышение попыток, нет email, неизвестный identifier, rate-limit, email обязателен
  при регистрации.
- E2E приложения через ADB (полный поток сброса + регистрация с email).
- Веб через прямые API-запросы + ручная проверка.
- Проверка, что письмо с кодом реально доходит.

## Секция 4 — Выкат и валидация трения (требование пользователя)

Главный риск — лишнее трение на входе отсекает клиентов. Поэтому:

1. **Сначала превью, потом прод.** Веб-часть выкатывается на превью-страницу
   (как делали с `preview.html`), сборка приложения — отдельный тестовый APK на
   устройство. Пользователь **вживую тестирует** регистрацию (с email) и полный
   поток восстановления.
2. **Критерий приёмки трения:** регистрация добавляет ровно одно поле (email) с
   понятной подписью; поток сброса — максимум 2 коротких экрана. Пользователь
   подтверждает, что это не отпугивает клиентов.
3. **Запасной рычаг (если на превью трение великовато):** сделать email
   необязательным на входе + обязательное напоминание добавить email перед первым
   заказом / в профиле. Меняет только правило валидации `register`, остальной дизайн
   не затрагивает.
4. В прод (сайт + приложение/стор) — только после явного одобрения после превью.
